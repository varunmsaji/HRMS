### K-1 analysis (static, read-only — nothing executed against a database)

**Correction found in the A1 review:** `002_app_role.sh` grants `SELECT, INSERT, UPDATE, DELETE` (no `TRUNCATE`) on all tables, and `test_the_runtime_role_can_truncate_no_table_at_all` asserts exactly that, so the K-1 exposure is **UPDATE and DELETE**; TRUNCATE is expected to be denied already (to be measured). The earlier wording "UPDATE/DELETE/TRUNCATE" came from the REVOKE statement in migration `20261009090000`, which revokes all three defensively.

**What is true (VERIFIED by reading):**

* `Punch` docstring (`modules/attendance/models.py:429`): "Never UPDATE'd or DELETE'd (WD-11 — punches immutable once written)".
* Migration `20261009090000_history_tables_append_only.py` revokes `UPDATE, DELETE, TRUNCATE` from `hrms_app` on **only** `leave_ledger`, `leave_application_action`, `audit_log`. Later migrations cover `email_log`, `leave_year_end_run`, `platform_audit_log` (the grants test lists six append-only tables). `punch`, `attendance_regularization_action`, `attendance_period_action` are not in any REVOKE (grep of `alembic/versions` for REVOKE shows no `punch` match).
* `infra/docker/postgres/init/002_app_role.sh` runs `GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES` (and default privileges for future tables). `test_runtime_role_grants.py` records that **re-running this script on a migrated database undid the REVOKEs** (reproduced 2026-10-25 for `leave_ledger`). So even the three/six protected tables depend on init-script discipline.
* No application source path updates or deletes a `Punch` (grep for `update(Punch)`, `delete(Punch)`, `UPDATE punch`, `DELETE FROM punch` under `src/` and `alembic/versions` found none; only `select(Punch)` reads in `attendance/repository.py`). The only DELETE of punch rows is the **test** helper `tests/integration/tenant_wipe.py`, which deletes from every table with `company_id`, run as the owner role in CI.
* No retention purge job exists for `TERMINATED` companies (`retention_until` is set but only read by the platform dashboard), so a future purge would need a privileged path — this is a design input to the fix.

**Impact (INFERRED):** a SQL-injection, a code defect in a new feature, or a compromised app credential could rewrite attendance history that payroll later trusts. No present code path does so.

**Reproduction plan (not run):** private disposable DB at head → connect as `hrms_app` with `app.company_id` set → inside a transaction that is **rolled back**, `UPDATE punch SET direction = direction WHERE false` is insufficient; instead assert via `has_table_privilege('hrms_app','punch','UPDATE'|'DELETE'|'TRUNCATE')` (the existing grants test style), then a rolled-back `UPDATE … WHERE id = :one_id`. Expected today: privileges `true` (defect present). Expected after approved fix: permission denied, 0 rows changed.

**Fix direction (for approval, not implemented):** new migration `REVOKE UPDATE, DELETE, TRUNCATE ON punch, attendance_regularization_action, attendance_period_action FROM hrms_app`; make `002_app_role.sh` not re-grant on append-only tables (or add a post-grant revoke); move the three tables into `APPEND_ONLY` in the grants test in the same change; give `tenant_wipe` and any future retention purge an owner-role path. Decide whether `punch` needs a narrow exception for face-data deletion obligations (face deletion code in `face_deletion.py` does not touch `punch`, per grep).
