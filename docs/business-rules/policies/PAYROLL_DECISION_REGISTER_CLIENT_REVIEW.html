02

Three kinds of decision

Every question in §3 is tagged with one of these. Getting the tag right matters more than getting the default right — a wrong default is a config change; a platform rule mistaken for a tenant setting (or the reverse) is a schema and UI rework.

Platform rule

Fixed behaviour, identical for every tenant. No settings screen, no override.

Example: a finalised pay run can never be edited — only corrected forward as an arrear.

Tenant setting

Every company configures this for itself, on its own timeline, independent of every other tenant.

Example: whether PF/ESI apply, and to which state's PT slab — this company's registrations, not a global switch.

Default template

What a brand-new signup sees before they've touched anything — pre-filled, fully editable, never mandatory.

Example: a standard Indian salary-structure template offered at onboarding, replaceable with the company's own.

4 items

These decide what belongs in the tenant-settings schema versus what's shared platform logic — get this backwards and the computation engine has to be re-keyed later.

1. How should a month's pay-days be counted? FR-PAY-008

Config
Question

Calendar days, actual working days, a fixed 26-day month, or a fixed 30-day month, with unpaid leave deducted from that base — this varies genuinely by company, so it's a per-tenant setting, not a platform constant.

Recommended answer

Build it as a company-level setting with four options, defaulting new signups to Fixed 30-day — the most common convention in Indian services/IT payroll and the easiest for an employee to reason about. Once a tenant's first pay run has been finalised, lock the setting for that tenant — changing it retroactively would silently reshape every past payslip's math.

2. How does a tenant tell the product which statutory registrations apply to them? FR-PAY-005

Config
Question

PF, ESI, Professional Tax (and which state), Labour Welfare Fund, Gratuity, and Bonus Act applicability are different for every company that signs up — a 2-person startup and a 500-person manufacturer aren't the same. This can't be answered once; it needs a real setup flow.

Recommended answer

A guided "Company Statutory Setup" step in onboarding: which states the company operates in, headcount per legal entity, and toggles for PF/ESI/LWF with their registration numbers. Pre-select PF and ESI as likely-on above the thresholds where they're legally mandatory (informational nudge, not an enforced rule — the tenant can still turn them off if genuinely exempt).

3. Who maintains the actual PF/ESI/PT/TDS rate values, and for how many tenants at once? FR-PAY-005, ADR-0011

Platform
Question

These rates are set by the government, not by any individual company — every tenant in Maharashtra owes the same PT slab as every other tenant in Maharashtra. Should each tenant maintain their own copy, or is this shared reference data?

Recommended answer

One shared, platform-owned statutory_master table, keyed by jurisdiction and effective date, read by every tenant's pay run but writable only by the platform team (with a compliance consultant's sign-off on every rate change). This is meaningfully simpler than per-tenant copies — one update, on the day the government changes a rate, correctly reaches every customer at once instead of 200 separate configuration tasks.

4. What salary structure does a new tenant start with? FR-PAY-001, FR-PAY-003, FR-PAY-004

Default
Question

Every tenant needs their own component set (Basic, HRA, Special Allowance, etc.) and their own CTC-to-net logic — but nobody signing up wants to build that from a blank canvas on day one.

Recommended answer

Ship 2–3 starter templates a new tenant picks from at setup — a standard white-collar template (Basic 40–50% of CTC, HRA 40–50% of Basic by metro/non-metro, remainder as Special Allowance) and a blue-collar/wage-earner template — fully editable afterward, never locked to the original choice. This is the single highest-leverage thing for a good first-signup experience; a blank component builder on day one is a real activation-rate risk.

High — needed before the first real tenant onboards

3 items

Each of these shapes a settings screen or an onboarding step — cheaper to design once than to retrofit after tenants are already using it.

5. What's the pay cycle and pay date? FR-PAY-007

Config
Question

Monthly is assumed — but the actual credit date (last working day, 1st, 7th of the following month) genuinely differs by company, and can even differ by legal entity within one tenant.

Recommended answer

A per-legal-entity setting, defaulting to last working day of the month for a new signup — the most common Indian convention, so most tenants will never need to touch it.

6. Who approves a pay run before it's finalised? FR-PAY-007

Config
Question

A pay run moves draft → computed → review → approved → finalised → paid. Small tenants may want one approver; larger ones want HR then Finance. Should the number of approval stages be configurable per tenant?

Recommended answer

Yes — a tenant-configurable approval chain (1 or 2 stages), defaulting new signups to a single approver so a 5-person company isn't forced into a two-person sign-off it doesn't have staff for. The no-self-approval rule underneath it, however, is a platform rule with no override — the same one already locked for attendance and leave.

7. Does leave cancel overtime on the same day — one platform answer, or per-tenant? Attendance–Leave review, Decision 1

Config
Question

The earlier Attendance & Leave review flagged this as unresolved. Attendance policies are already assignable per company/department/individual, so this naturally becomes a policy-level setting rather than one global answer — different tenants genuinely pay this differently.

Recommended answer

Expose it as a toggle on the existing attendance policy object, defaulting new policies to "leave cancels overtime" (the safer, harder-to-mispay default). This still has to be resolved before Payroll's first real run reads the data — it just lives in Attendance's settings, not a new Payroll-specific one.

Low — fine to settle later, per tenant as it comes up

8. Should a rejoining employee's PF number carry forward automatically? Statutory module, open question

Platform
Question

When someone who previously left a company rejoins, should their earlier PF number be pre-filled, or re-entered fresh each time?

Recommended answer

Pre-fill it as a suggestion HR can override, the same behaviour for every tenant — most rejoining employees keep the same UAN/PF number, but this doesn't vary by company, so it doesn't need its own setting.

9. Rounding rule for computed pay components FR-PAY-001

Default
Question

When a formula produces a fractional rupee amount, should it round to the nearest rupee, always down, or always up?

Recommended answer

Ship one sensible default for every new tenant — nearest rupee for earnings, round down for statutory deductions — and don't expose it as a setting unless a real tenant asks; it's the kind of knob that mostly adds surface area without anyone actually needing it.

04

What happens after these are answered

The four critical items decide the shape of the tenant-settings schema itself — get those tagged correctly as platform-vs-config-vs-default and the computation engine work already in progress can be built against that schema instead of guessing at it. The high-priority items should be settled before the first real tenant's first pay run; the low-priority items can land alongside their own settings screens as those get built. Every "Config" item here is a settings screen that has to exist somewhere in the product — the recommendation is the default value it ships with, not the only value it will ever hold.
