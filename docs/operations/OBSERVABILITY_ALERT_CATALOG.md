# Observability alert catalog

> **Status.** The rules exist as code in [`infra/monitoring/prometheus/alerts.yml`](../../infra/monitoring/prometheus/alerts.yml) and are syntax- and behaviour-tested with `promtool` (see [Verification](#4-verification)). **No Prometheus, Alertmanager or notification destination is deployed or approved, so no alert can currently notify anyone.** Delivery has *not* been tested.
>
> **Every threshold is provisional.** They are conservative starting values chosen from first principles (gunicorn timeout 60 s, heartbeat every 60 s, daily/hourly Beat schedules), not calibrated against production traffic, because none exists yet. Section 3 says how to tune them.

## 1. Routing and ownership (open decision)

| Item | Value |
|---|---|
| Notification destination | **UNDECIDED** (D1 in the architecture doc): e-mail relay, chat webhook or pager. Until chosen, rules only show in the Prometheus UI. |
| Owner / escalation | **UNASSIGNED** - needs a named on-call owner per severity. |
| Severity meaning | `critical` = act now, service or scheduled business job is down; `high` = act within working hours / the hour; `warning` = review daily. |
| Existing channel | `infra/monitoring/hrms_monitor.sh` (cron, log-grep based) remains the only implemented alerter; it covers overlapping failure modes and stays useful as a second, independent signal. |

## 3. Tuning provisional thresholds

1. Run Prometheus with alert delivery **off** for 2-4 weeks including at least one month-end and one payroll cycle.
2. For each alert, graph its expression over that period (the dashboards in [OBSERVABILITY_DASHBOARD_CATALOG.md](OBSERVABILITY_DASHBOARD_CATALOG.md) already plot most of them) and note how often it would have fired and whether each firing was actionable.
3. Set latency thresholds just above the observed busy-hour p95/p99 of healthy days; set rate thresholds (`login.failed`, retries) at roughly 3x the observed 95th-percentile quarter-hour.
4. Raise `for:` before raising a threshold if the problem is flapping; lower it only for `critical` rules.
5. Record the chosen values and the baseline they came from in this file, replacing 'provisional'.

## 5. Alerts the metrics cannot express (gaps)

- **Host CPU/RAM** alerts need `node_exporter` (optional compose file); only the log volume's free space is exported by the application itself.
- **PostgreSQL deadlocks, lock waits and long transactions** need server-side logging or `pg_stat_*` access that is not enabled (approval required; see architecture doc section 5). Pool exhaustion and statement latency are covered.
- **Per-worker liveness** is inferred from the Beat heartbeat; there is no per-worker series (the Docker `inspect ping` healthcheck covers a single worker container).
- **Pay-run 'stuck' state** is not detectable from metrics: payroll executes synchronously inside API requests (no Celery task), so a stuck run appears as slow/failed `payroll.pay_run.*` operations, not as a queued job.
