## 2. Metrics

`infra/monitoring/prometheus/prometheus.yml` scrapes `api:8000/metrics` with a bearer token file and `node-exporter:9100` every 30 seconds. Retention in the compose command is 15 days or 2 GB. The token file is gitignored under `infra/monitoring/prometheus/secrets/`.

Application metrics are implemented in `apps/api/src/hrms/core/observability/` and include HTTP counts and latency, dependency up/down, Celery queue depth, task failures, and a scheduler heartbeat. Alert rules in `infra/monitoring/prometheus/alerts.yml` reference those names. The rules file is coherent and commented as provisional. It is not loaded, because Prometheus is not running.

There is no postgres_exporter, redis_exporter, or celery-exporter container. Database and Redis health are meant to appear as `hrms_dependency_up` from the API process. Queue depth is meant to appear as `hrms_celery_queue_depth` from the same process. If the API is up and the worker is wedged, the heartbeat rule would catch Beat-to-worker failure only when something evaluates the rule. Today the host monitor calls `python -m hrms.ops.job_health` inside the worker container. That path is the one that is actually scheduled.

VPS metrics from node_exporter are not collected. The monitor does collect disk percentage, container health, and restart counts on its own, by shell.

## 3. Dashboards

`docs/operations/OBSERVABILITY_DASHBOARD_CATALOG.md` says the JSON files are definitions, Grafana is not installed, and panel usefulness was not proven against production traffic. This audit confirms Grafana is still absent. The four files are:

- `infra/monitoring/grafana/dashboards/hrms-a-system-overview.json`
- `hrms-b-api-performance.json`
- `hrms-c-background-jobs.json`
- `hrms-d-hrms-operations.json`

They are generated by `infra/monitoring/grafana/generate_dashboards.py`. Nothing provisions them.

## 4. Alerting

Prometheus rules exist for API down, database down, stale scheduler, missed leave and attendance jobs, payroll failures, disk, object storage, log write failures, 5xx rate, unhandled exceptions, latency, queue backlog, Redis, and further rules below line 200 of `alerts.yml`. They do not page anyone.

The live alert path is `hrms_monitor.sh` every five minutes:

- `/health/ready` inside the API container
- `job_health` inside the worker
- unhealthy containers and restart counts
- disk use
- structured log events in a five-minute window
- backup log age and failure lines

On failure it pipes JSON to `hrms_notify_email.py`, which sends SMTP mail and suppresses the same failure set for `ALERT_REPEAT_HOURS` (default 6). systemd `OnFailure=hrms-alert@.service` mails the journal when the unit itself crashes. The monitor's exit code 1 (checks failed) is a success for systemd (`SuccessExitStatus=1`), so a failing health check does not also page through `OnFailure`. That is intentional, so the script is the only mailer for check failures.

What this audit verified: the timer is active and the last run exited 0. What it did not verify: that SMTP accepts a message. A green run does not send mail. Claiming that alerts work would repeat the mistake the brief forbids.

Missing-data behaviour for Prometheus (`absent()` rules) is written and not in effect. The host monitor treats a failed `job_health` invocation as a failed check. That is the missing-data behaviour that is actually deployed.

There is no severity routing beyond the JSON field and the email subject. There is no inhibition. Deduplication is the six-hour hash in the email script, for the monitor path only.

## 5. Logging

| Property | Status |
|---|---|
| Structured JSON from the API | Implemented in code (`structlog`). Running containers were not tailed |
| Request ID | Implemented in API and in the repo nginx map. Host nginx file was not fully compared |
| Correlation into the worker | Celery signals in `celery_app.py` copy a trace parent. Not observed in a live task |
| File logs | Volume `api_logs`, rotation settings in the production example (`LOG_FILE_MAX_BYTES`, backup count, retention days) |
| Docker json-file caps | 10 MB × 5 on each HRMS service in the vps file |
| Host logrotate | Timer active |
| Central store | Missing. No Loki, Elasticsearch, or CloudWatch |
| Search | `docker logs` and files on the host. No index |
| Redaction | Implemented and unit-tested. Not sampled in production logs |
| Retention | Application files 30 days in the example. Docker caps are by size, not by day. Host nginx logs follow host logrotate. Exact live logrotate rule was not opened |

Error reference IDs: the application error-handling work on `test` (commits dated 2026-11-25, message prefix `ERR`) is not in the 2026-11-04 image. Production does not yet have that behaviour.

## 6. Exception tracking

No Sentry, GlitchTip, or Rollbar project is configured. Client and server exceptions are logs. Grouping and deduplication of exceptions do not exist beyond the email script's check-name hash. Privacy safeguards for an error tracker are not applicable until one is introduced. The recommendation is to keep logs and the monitor until volume justifies a tracker, and to add one only for unhandled 500s with the existing redaction. That is `P5-04` in the plan. It is not a prerequisite for a safe release.

## 7. What an operator can see today

Without adding software, an operator can:

- `curl` the public health URLs (both returned 200 once during this audit; live took 5.6 seconds, ready took 0.7 seconds; one sample is not a latency baseline).
- Read `systemctl status` for the monitor and the backup.
- Read `/var/backups/hrms/postgres/backup.log` success and failure lines.
- `docker ps` and `docker stats`.

An operator cannot, today, open a dashboard of request rate, p99, queue depth, or Postgres connections. Those series are not being stored.
