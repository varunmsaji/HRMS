Not production-ready · 5 blockers

The domain is further along than the platform around it.

The HR logic — tenant isolation, RBAC data scopes, attendance calculation, leave ledgers — is built to a genuinely high standard, with a real Postgres RLS backstop under a non-privileged runtime role and 1,220 tests behind it. That part is close.

What is not finished is the layer that makes it deployable and defensible: the API cannot be reached by a browser in production as configured, JWT signing secrets have working defaults with no guard, the login endpoint is unthrottled, government ID and bank numbers are stored in plaintext despite _enc column names, and no list endpoint in the entire API is paginated.

None of the five blockers is a deep architectural problem. All five are a focused week of work — but all five must land before a paying tenant's data goes in.

Blockers

P0 · 5 findings

Each of these either prevents the product from functioning once deployed, or exposes customer data in a way that is not defensible to a client or a regulator.

P0OPS-01

Production CORS allows no origins at all

apps/api/src/hrms/app.py:38 — allow_origins=["*"] if settings.is_development else []

Outside development the allowed-origin list is empty and there is no environment variable to populate it. The moment the API runs with ENVIRONMENT=staging or production, every browser request from the Next.js app is blocked by the preflight. The application is undeployable as configured — this fails on the first deploy, not later under load.

The development branch has its own defect: allow_origins=["*"] together with allow_credentials=True is an invalid combination that browsers reject, so the wildcard is providing less than it appears to.

Fix: add a cors_allowed_origins setting, read it per environment, and fail boot if it is empty outside development.

P0SEC-01

JWT signing secrets have working defaults and no production guard

apps/api/src/hrms/core/config/settings.py:27–30 — jwt_access_secret default "change-me-local-dev-only-min-16"

Both signing secrets carry defaults that satisfy the 16-character minimum, so an environment that forgets to inject them boots successfully and signs tokens with a value that is public in the repository. Anyone with the source can then mint a valid access token for any user_id/company_id pair — a complete authentication bypass across every tenant, with no log trace, because such a token verifies normally.

Nothing in the settings model, the app factory or the lifespan hook asserts that production is not running on defaults. The production env template correctly documents Secrets Manager injection, but that is documentation, not enforcement.

Fix: a Pydantic model validator that raises when environment != "development" and either secret matches the default or falls under a real entropy floor.

P0SEC-02

No rate limit on login or token refresh

apps/api/src/hrms/modules/identity/router.py:34–60 — neither route takes the _password_rate_limit dependency

Registration, forgot-password, reset-password and invite-acceptance all carry a 10-per-minute IP bucket. Login and refresh — the two endpoints that actually validate credentials — carry none. The only control is per-account lockout after five failures, which does not stop password spraying across many accounts, and which an attacker can aim at any known email address as a denial-of-service primitive against that user.

Refresh is also unthrottled, so a stolen refresh token can be exercised without friction.

Fix: apply the existing rate_limit("auth", …) dependency to both routes, keyed on email as well as IP, and make the limiter fail closed if Redis is unreachable.

P0DATA-01

Aadhaar, PAN and bank account numbers are stored in plaintext

apps/api/src/hrms/modules/employee/models.py:61–63 (pan_number_enc, aadhaar_number_enc) · :272 (account_number_enc)

The _enc suffix implies encryption at rest; the columns are plain String and a search for any encryption primitive across the API — Fernet, KMS, pgcrypto, application-level envelope encryption — returns a single source comment acknowledging the gap. Government identifiers and salary-account numbers for every employee of every tenant sit in cleartext in one table.

This is the finding most likely to end a client security review. Under India's DPDP Act these are precisely the identifiers that attract the strictest handling expectations, and a database snapshot, a replica, a backup file or a support export leaks all of them at once. It also blocks payroll, which is where bank details become operationally necessary rather than optional.

Fix: envelope-encrypt these three columns with a KMS-managed data key, decrypt only in the narrow service paths that need the value, and mask in every read schema. Backfill before the first real tenant, not after.

P0API-01

No list endpoint in the API is paginated

apps/api/src/hrms/shared/pagination.py:14 — PaginationMeta defined, zero usages · employee/router.py:97 list_employees takes no page parameters

Across 228 routes, not one list endpoint accepts a page, cursor or limit parameter; every one serialises the tenant's full result set. GET /employees returns every employee, attendance-day and punch listings return every row in range, and the users list additionally runs one role query per member.

At demo scale this is invisible. At a thousand-employee tenant with a year of attendance history it is a slow-query and memory problem on every page load, and an authenticated amplification vector: one cheap request forces an unbounded database read and JSON serialisation.

Fix: wire the already-defined PaginationMeta through ListEnvelope, add page/per_page with a hard server-side ceiling, and bound the date ranges on attendance and leave queries.

High severity

P1 · 9 findings

Not launch-stopping on their own, but each one materially widens the blast radius of an incident. Fix before onboarding customers, not before the first internal deploy.

P1SEC-03

Public document upload buffers the entire request before checking size

apps/api/src/hrms/modules/onboarding/public_router.py:94 — body = await file.read() · service.py:566 — size checked after

The 10 MB ceiling is enforced only after the whole file is resident in process memory, on a route reachable by anyone holding an onboarding link and with no rate limit attached. A handful of concurrent large uploads is enough to exhaust the API worker.

Fix: reject on Content-Length before reading, stream in bounded chunks, and add the auth rate-limit bucket to the public onboarding router.

P1SEC-04

Uploaded content type is caller-controlled and replayed on download

apps/api/src/hrms/modules/onboarding/service.py:564–572 — document_type validated, content_type is not; filename interpolated into the S3 key

Only the document category is validated against an allow-list. The MIME type comes straight from the client, is stored on the object, and is later served to an HR reviewer through a presigned GET with no Content-Disposition: attachment — so an uploaded text/html file executes in the browser on the bucket origin. The raw filename is also concatenated into the object key without sanitisation, and nothing scans uploads for malware.

Fix: allow-list MIME types, sniff the magic bytes rather than trusting the header, sanitise the key segment, and force an attachment disposition on presigned reads.

P1SEC-05

No security headers on either application

apps/api/src/hrms/app.py:36–43 — only CORS and tenancy middleware · apps/web/next.config.mjs — no headers()

No Content-Security-Policy, HSTS, X-Content-Type-Options, frame-options or referrer policy is emitted anywhere. The missing CSP matters most because it is the layer that would contain the next finding.

Fix: a response-header middleware on the API and a headers() block in the Next config, CSP included.

P1SEC-06

Thirty-day refresh tokens live in localStorage

apps/web/src/lib/auth/token-storage.ts:1–13 — documented tradeoff, no HttpOnly cookie is set by the API

The module is honest about the tradeoff and correctly isolated for a later swap. The risk is the combination: any XSS on the app — with no CSP to blunt it — yields a long-lived refresh token, and therefore durable account takeover that survives a password change, since a reset does not revoke token families (SEC-07).

Fix: move the refresh token to an HttpOnly, Secure, SameSite cookie; the API already accepts one at /auth/token/refresh, it simply never sets it.

P1SEC-07

Password reset leaves existing sessions alive

apps/api/src/hrms/modules/identity/service.py:314–341 — updates the hash; no session or refresh-family revocation

The reset itself is well built — single-use hashed token, two-hour TTL, identical error for every failure mode. But the user's own reason for resetting is usually "someone else may have my account," and an attacker's existing session and refresh family both survive it. There is also no audit record for the credential change, by deliberate design, because the audit table requires a company context a reset does not have.

Fix: revoke all sessions and refresh tokens for the user inside the reset transaction, and give the audit log a nullable-tenant path for identity events.

P1SEC-08

Invite acceptance authenticates an existing account without its password

apps/api/src/hrms/modules/account_invite/service.py — existing-user branch, then issue_tokens_for(user_id=…)

When an invite is sent to an address that already has an account, acceptance adds the membership and immediately issues that user a session — the password supplied on the accept form is never checked against the existing hash. Whoever holds the emailed link gets an authenticated session as that person, scoped to the inviting company, and the response also enumerates the names of every other company that account belongs to.

The sensible behaviour is already implied by the code: it deliberately does not overwrite the existing password. It should likewise not grant a session.

Fix: for an existing user, require a normal login (or verify the submitted password) before attaching the membership, and drop other-company names from the public response.

P1OPS-02

Client IPs are not resolved behind a proxy

apps/api/src/hrms/shared/rate_limit.py:49 — request.client.host · no ProxyHeadersMiddleware in app.py

Every rate-limit bucket is keyed on the socket peer. Behind a load balancer that is the balancer, so registration, forgot-password and invite-acceptance collapse into a single shared counter for all traffic — simultaneously trivial to exhaust for legitimate users and useless against an attacker. Logged IPs on sessions and audit records are wrong for the same reason.

Fix: enable proxy-header handling with an explicit trusted-hosts list; never trust X-Forwarded-For unconditionally.

P1SEC-09

Registration creates unverified tenants and signs the creator straight in

apps/api/src/hrms/modules/organisation/router.py:108 — public, IP-throttled, returns a token response

No email verification exists anywhere in the codebase. Any address — including one the registrant does not control — produces a live trial company with a COMPANY_ADMIN session, and the address is then permanently bound to that tenant under a global unique constraint on user.email, which lets a bad actor squat a real company's address. Combined with the shared IP bucket above, tenant creation is effectively unbounded.

Fix: require a verified email before the tenant leaves a pending state, and treat unverified tenants as disposable.

P1DEP-01

JWT handling depends on an unmaintained library

apps/api/pyproject.toml — python-jose[cryptography]>=3.3.0 · core/auth/jwt.py

python-jose is effectively unmaintained and carries published algorithm-confusion and denial-of-service advisories (CVE-2024-33663, CVE-2024-33664). The application's own usage is careful — HS256 pinned on both encode and decode, token type asserted — so this is a supply-chain exposure rather than an exploitable bug today. No dependency scanning runs in CI to catch the next one.

Fix: migrate to PyJWT (a small, contained change given the pinned algorithm) and add pip-audit plus npm audit to the pipeline.

Database & tenant isolation

Schema review

68 linear migrations, 81 tables, timezone-aware timestamps throughout, money as integer minor units, GiST exclusion constraints preventing overlapping effective-dated rows, and no destructive cascade on any HR fact. The modelling is strong. The gaps are in coverage at the edges rather than in the core design.

ControlStateDetail
Runtime role Strong The app connects as hrms_app — NOSUPERUSER, NOBYPASSRLS, owns nothing. CI asserts those attributes before the security suite runs, so the RLS tests cannot pass vacuously.
Policy coverage Strong 67 tenant tables carry ENABLE + FORCE ROW LEVEL SECURITY with a tenant_isolation policy. An unset session variable yields zero rows — it fails closed.
RLS on company No-op 001_init_schema.sql:464 issues FORCE without ENABLE, which does nothing in Postgres. The table's comment reasons it away as the tenant root, but the practical effect is no backstop on company rows.
Identity tables Uncovered user, session, refresh_token, password_reset_token, user_role, role_permission and permission have no policy. Cross-company by nature, so this is defensible — but it means application WHERE clauses are the only control there.
Deliberate exemptions Documented onboarding_token and account_invite are explicitly exempt so a pre-tenant-context lookup can resolve them; both are hash-keyed and both set the GUC immediately after resolving.
Pre-auth GUC Footgun TenancyMiddleware sets app.company_id from an unverified X-Company-Id header; get_tenant_context re-sets it from the verified JWT. Correct for every route today, fail-open for any future route that forgets the dependency.
PII at rest Blocked See DATA-01 — _enc columns hold plaintext.
Migration rollback Partial The chain is linear and unbroken with real downgrade() bodies, except the base revision, which raises NotImplementedError. No downgrade is exercised in CI.
Backup & restore Undefined No documented backup cadence, retention, restore drill or RPO/RTO target anywhere in the repository.

Worth stating plainly: tenant isolation here is better than most multi-tenant products reach before their first customer. The database itself — not a forgotten WHERE clause — is what stops a cross-tenant read, and there is a test suite that opens its own restricted connection to prove it. That foundation is why the remaining findings are fixable in days rather than months.

What is already solid

Verified strengths

Assessed with the same scrutiny as the findings. These are load-bearing and should not be disturbed while fixing the rest.

Refresh-token rotation with family revocation

Every refresh revokes and reissues; replaying a spent token revokes the entire family and its sessions. Textbook.

Per-request session validation

Every authenticated request re-checks user status, session revocation and active company membership against the database — not just the token signature.

Fail-closed permission resolution

An empty data scope raises rather than defaulting to company-wide, and writes verify the target record's visibility, not merely that the caller holds the permission.

404 instead of 403 across tenants

Out-of-scope and nonexistent identifiers return identical responses, so the API cannot be used to probe for record existence.

Server-assigned punch instants

The self-punch schema has no punch_time, source or employee_id field and rejects extras outright — closing the clock-trust risk flagged in the September timezone audit.

Anti-enumeration throughout

Login, forgot-password, invite and onboarding token resolution all return one identical response for every failure mode.

Enforced engineering gates

1,220 tests, mypy --strict, ruff lint and format, import-linter module boundaries, and CI pinned to UTC so a host-clock regression fails the build.

Period locks on every write path

Closed attendance periods are checked at thirteen separate mutation sites, with unlocking gated behind a permission distinct from period management.

Go-live sequence

Ordered remediation

Ordered by dependency and risk, not by effort. Steps 1–5 clear the blockers; 6–8 are the minimum bar for handling a real customer's data; 9–10 are what make an incident survivable.

  1. Make the API reachable and its secrets mandatory

    Environment-driven CORS origins, plus boot-time validation that refuses to start on default JWT secrets outside development.

    OPS-01, SEC-01

  2. Throttle the credential endpoints

    Rate-limit login and refresh by IP and by email, and resolve the real client IP behind the proxy so every existing bucket starts working.

    SEC-02, OPS-02

  3. Encrypt the identifiers

    Envelope-encrypt PAN, Aadhaar and bank account columns; mask them in read schemas. Do this before the first tenant, while backfill is still cheap.

    DATA-01

  4. Paginate every list endpoint

    Wire the existing PaginationMeta through the list envelope with a server-side ceiling, and bound the attendance and leave date ranges.

    API-01

  5. Harden the two public write surfaces

    Size-check before buffering, allow-list MIME types, sanitise object keys, force attachment disposition, and rate-limit the public onboarding router.

    SEC-03, SEC-04

  6. Close the session-lifecycle gaps

    Revoke sessions and token families on password reset; require a real authentication before an invite attaches a membership to an existing account.

    SEC-07, SEC-08

  7. Add security headers and move the refresh token to a cookie

    CSP, HSTS and the rest on both apps; an HttpOnly refresh cookie the API already knows how to read.

    SEC-05, SEC-06

  8. Verify email before a tenant becomes real

    Hold new companies in a pending state until the admin address is confirmed, so unverified tenants are disposable rather than permanent.

    SEC-09

  9. Turn on the lights

    Error tracking in the 500 handler, request access logging with the existing request id, a Redis-aware readiness probe, and a defined limiter failure policy.

    OBS-01, OBS-02, OPS-03, SEC-11

  10. Finish the delivery pipeline

    A non-root API image with a health check, a web container and build step, dependency and container scanning, and a documented, rehearsed backup restore.

    OPS-04, OPS-05, QA-01, DEP-01
